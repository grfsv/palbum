# 📱 写真整理・共有アプリ設計書

## I. 🌟 企画骨子とコンセプト (Project Core and Concept)

### 基本方針

| 項目 | 決定事項 |
|------|----------|
| **目的** | フレンド間の写真整理と共有の自動化に特化。既存の関係性の強化に集中し、マッチングなどの追跡リスクのある機能は完全に排除。 |
| **最優先事項** | 行動追跡の絶対防止 |

### 位置情報の取り扱い

- 連続的なGPSログの収集・送信を完全に禁止
- 位置情報は、写真のGEOタグとサーバーへの単発クエリのみで利用

### 接触検証

- **RPI (Rolling Proximity Identifier)** の利用
  - IDを定期的に変更・暗号化し、追跡を不可能にする
  - 検証はサーバーがDTKを用いて行い、匿名性を維持

### セッションの定義

- メンバー離脱後もセッションIDは維持し、残ったメンバーで継続
- 記録の連続性を優先し、離脱者には個別終了時刻 (Individual_EndTime) を設定する

## II. 💡 主要機能とロジック (Key Features and Logic)

### 1. セッションの確立と管理

| 機能 | ロジックの仕組み | 特筆事項 |
|------|------------------|----------|
| **セッション確立** | 相互にフレンド登録されているペア間で、RPIの継続的双方向検証が一定時間以上成立した場合にセッション（MatchID）を確定。 | 非フレンドとの接触は一切記録されない。 |
| **途中離脱対応** | サーバーは離脱メンバーの Individual_EndTime を確定するが、MatchID は残りのメンバーで維持。 | ユーザー体験における「遊び」の流れを分裂させず、記録の精度を担保。 |
| **遡及的セッション** | AとCが後からフレンドになった場合、サーバーは過去の ContactSummary を参照し、過去の接触記録に基づき新たなセッションを遡及的に作成する。 | ユーザーが「昔遊んだ記録」を後から取り戻せるようにする。 |

### 2. 写真整理と場所情報の特定

| 機能 | 処理主体 | 詳細なロジック |
|------|----------|----------------|
| **場所名の決定** | クライアント | セッション時間内の写真GEOタグを収集し、写真枚数が最も多いクラスターの座標を代表地として選定。 |
| **逆ジオコーディング** | サーバー | クライアントから送られた代表座標に対し、施設名を返す単発クエリを実行。サーバーはGEOタグを永続的に保存しない。 |
| **写真の分類** | クライアント | 写真を MatchID に紐づけ、Source_Type で MY_SHOT（自己撮影）と SHARED（共有）を厳密に分離。 |

## III. 🔒 セキュリティとBLE実装

### 1. RPI生成と検証のアルゴリズム

RPI生成は、DTK（日次追跡鍵）を鍵とするAES-128アルゴリズムを用いて行われます。

**RPIの生成:**

$$\text{RPI} = \text{AES-128}_{\text{DTK}}(\text{TI})$$

**検証の高速化:**

サーバーは、受信した $DTK_{ID}$ で正しいDTKを特定し、$TI$（時間間隔番号）を用いて1回の暗号計算でRPIを再現・照合します。

### 2. BLEアドバタイズの最終ペイロード構成

| 要素 | 役割 | 長さ (バイト) | 備考 |
|------|------|---------------|------|
| **Flags** | OSがデバイスの動作モードを識別するための必須情報。 | 3 | - |
| **Manufacturer ID** | アプリ固有の識別子。 | 2 | Manufacturer Specific Data (0xFF)内に格納。 |
| **RPI** | ローリング近接識別子。 | 16 | AES-128による出力。 |
| **$DTK_{ID}$** | サーバーがDTKを特定するための鍵識別子。 | 4 | - |
| **$TI$** | RPIが生成された時間間隔番号。 | 2 | サーバーの検証を高速化するために必須。 |
| **合計** | - | **29バイト** | BLEペイロードの31バイト制限内に収まる。 |

## IV. 💾 データモデリング (Data Modeling)

### 1. サーバー側データモデル（整合性と効率性）

| テーブル名 | 役割 | 主なカラム | 構造上の目的 |
|------------|------|------------|--------------|
| **Matches** | セッションのコア情報 | MatchID, StartTime, place_names (リスト) | セッションの基本情報を提供。 |
| **SessionMembers** | メンバーシップと個別終了時刻 | MatchID, UserID, Individual_EndTime | セッション継続ロジックの核。途中離脱者の正確な記録。 |
| **ContactSummary** | 匿名接触の要約 | RPI_Seen_1, RPI_Seen_2, Date, Duration | 遡及的セッション作成時、過去ログ検索を高速化する中間データ。 |
| **RawLogs** | RPI受信の一次証拠 | RPI_ID, Timestamp, RSSI | 最終的な検証に使用される元データ。GPSログは持たない。 |

### 2. クライアント側ローカルDBモデル（UXとデータ保持）

| テーブル名 | 役割 | 主なカラム | UXへの貢献 |
|------------|------|------------|------------|
| **LocalPhotoMetadata** | 写真の基本情報 | File_Path, Shooting_Time, GEO_Tag | - |
| **SessionPhotoLink** | 写真とセッションの紐付け | MatchID, File_Path, Source_Type (MY_SHOT / SHARED) | 共有された写真と自己撮影写真の明確な分離。 |
| **DisplayCache** | ビューア表示の高速化 | MatchID, Session_Name, Location_Summary | 画面表示の際に複雑な計算やDB参照を不要にするためのキャッシュ。 |
